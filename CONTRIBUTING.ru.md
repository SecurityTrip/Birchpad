# Участие в Birchpad

[English](CONTRIBUTING.md) · Русский

Спасибо за интерес к Birchpad!

## Прежде чем начать

- Для всего, что больше небольшого исправления, сначала откройте issue или обсуждение, чтобы
  договориться о подходе.
- Архитектурные решения записаны в [`docs/adr`](docs/adr). Если ваше изменение противоречит
  одному из них, предложите новый ADR вместо того, чтобы тихо отступать от него.

## Разработка

```bash
cargo fmt --all
cargo clippy --workspace --all-targets
cargo nextest run --workspace
```

[`cargo-nextest`](https://nexte.st) (`cargo install cargo-nextest --locked`) запускает каждый
тест в отдельном процессе, столько сразу, сколько ядер; `cargo test --workspace` выполняет те же
тесты медленнее, один тестовый исполняемый файл за другим. Doc-тестов в crate'ах нет — nextest
их бы не выполнял; примеры — это тесты. Его настройки — в `.config/nextest.toml`. Отладочные
сборки оптимизируют зависимости (`[profile.dev.package."*"]` в `Cargo.toml`): тесты окна
проводят большую часть времени в GPUI, а тестовое окно выключает анимацию (`set_reduce_motion`),
чтобы ни один тест не ждал, пока выплывет диалог.

CI выполняет те же команды, считая предупреждения ошибками, в четырёх процессах, которые
стартуют вместе при каждом push в `main` и каждом pull request, все их задания — параллельно:

- **Linux** (`.github/workflows/linux.yml`): Clippy, тесты и сквозные тесты в Ubuntu и тесты в
  контейнерах Debian trixie и bookworm с собственными библиотеками Debian;
- **Windows** (`windows.yml`): Clippy и тесты на x64 и ARM64, сквозные тесты на x64;
- **macOS** (`macos.yml`): Clippy, тесты и сквозные тесты;
- **Checks** (`checks.yml`): форматирование,
  [`cargo-deny`](https://github.com/EmbarkStudios/cargo-deny) для лицензий и уведомлений об
  уязвимостях, покрытие и фаззинг.

Названия заданий (`test (ubuntu-latest)`, `e2e (windows-latest)`, ...) — это проверки, которых
требует набор правил ветки `main`: задание, переименованное без правки этого набора, оставит
pull request ждать проверки, которая никогда не придёт.

Clippy работает в собственном задании рядом с тестами, а сборки в CI хранят из отладочной
информации только номера строк (`CARGO_PROFILE_DEV_DEBUG=line-tables-only`), чтобы тестовые
файлы быстрее компоновались и кешировались.

### Основные правила для кода

- `birchpad-core` никогда не зависит от crate'ов интерфейса. Всё в нём проверяется без окна.
- Логика, которой не нужно окно, живёт в crate'е своего рода (`core`, `io`, `config`, `tools`,
  ...), а не в приложении. То, что делят части окна (реестр команд, настройки приложения,
  кнопки диалогов, сообщения пользователю), — в `birchpad-ui`; обработчик команды
  регистрируется для вида, который её выполняет (`CommandTarget`), а не в реестре. Редактор
  (`birchpad-editor`) просит у приложения всё остальное через `EditorHooks`; слои описаны в
  ADR 0041.
- Позиции в модели текста — **смещения в байтах** в верёвке. Переводите их в символы, UTF-16 или
  видимые столбцы только на краях (отрисовка, LSP, строка состояния).
- Никаких тестов в `src`: тесты crate'а лежат в его папке `tests` и проверяют его через
  публичный интерфейс (ADR 0043). Большая часть — в одном тестовом исполняемом файле,
  `tests/integration`, чей `main.rs` называет модуль для каждой части `src`
  (`src/pane.rs` → `tests/integration/pane/tests.rs`); остальные (свойства, замеры времени,
  сквозные тесты) — файлы прямо в `tests`. То, что нужно только тестам, спрятано за
  возможностью `test-support` crate'а, которую включают его тесты; приложение — это библиотека
  (`src/lib.rs`) и программа, которая её запускает, чтобы тесты могли управлять его частями.
- Тестовые данные в `tests/fixtures` фиксируются байт в байт (см. `.gitattributes`); не давайте
  редактору «исправлять» их кодировку или концы строк.
- Никакого `unsafe` без комментария, объясняющего, почему это корректно, и рецензента, который
  согласен.

### Тесты

У Birchpad нет тестировщиков: его тесты и есть контроль качества. Для каждой функции или
возможности, которой касается изменение, тесты покрывают:

- **позитивный сценарий**: с обычными входными данными делается то, что должно;
- **негативный сценарий**: неверный ввод, отсутствующий или неправильный аргумент, отклонённое
  действие (документ только для чтения, файл, который нельзя прочитать или записать), путь
  ошибки. Всё завершается чисто, без паники и без изменения того, что меняться не должно;
- **граничные значения**: пустой текст, первая и последняя строка или символ, конец текста без
  завершающего перевода строки, ноль, единица и максимум, каждый предел и следующее за ним
  значение, CRLF, широкие и комбинируемые символы, очень длинные строки.

К исправлению ошибки прилагается тест, который без исправления падает. `cargo llvm-cov
--workspace` показывает код, который ещё не выполняет ни один тест; покройте его в первую
очередь. CI падает, когда доля выполненных строк crate'а опускается ниже его порога в
`.github/coverage-floors.toml`, а пороги только растут: поднимите порог в изменении, тесты
которого заметно поднимают покрытие crate'а.

Подсветка синтаксиса сравнивается со снимками (`crates/syntax/tests/snapshots`). Изменение
грамматики или запроса, меняющее цвета, валит тест и записывает новый снимок рядом со старым как
`.snap.new`; после проверки разницы примите новые снимки так:

```bash
BIRCHPAD_BLESS=1 cargo nextest run -p birchpad-syntax --test highlights
```

Новая зависимость — последнее средство: сначала проверьте `cargo tree --duplicates`,
предпочитайте то, что уже собирают рабочая область или GPUI, и выключайте ненужные возможности
по умолчанию. `.github/dependabot.yml` держит несколько crate'ов на версиях, которые использует
GPUI, чтобы собиралась одна копия.

Всё, что читает ввод извне (файлы и их кодировки, настройки, файл состояния, сессии и
`session.xml` Notepad++, файлы `.workspace`, раскладка клавиш, контекстное меню текста
(`context-menu.toml`), командная строка и сообщение, передающее её работающему экземпляру,
манифест обновлений и онлайн-каталог, `plugin.toml` плагинов, JSON, XML и шестнадцатеричные
дампы, которые читают встроенные инструменты, пути JSON, выражения XPath, DTD и XML Schema,
словари Hunspell, поисковые запросы и фильтры поиска в файлах, вызовы, которые плагины делают в
Birchpad, и скрипты Rhai), проходит фаззинг. Проверки находятся в `crates/fuzz`: каждая
принимает любые байты и проверяет больше, чем «нет паники» (то, что читается чисто,
записывается обратно так же). `cargo test -p birchpad-fuzz` прогоняет их по затравкам в
`fuzz/seeds`, по всем обрезкам каждой затравки и по нескольким сотням её мутантов
(`BIRCHPAD_FUZZ_MUTANTS=20000` — больше); CI ещё запускает каждую на минуту под libFuzzer. Для
долгого фаззинга, с ночным набором инструментов и `cargo install cargo-fuzz`:

```bash
cargo +nightly fuzz run session fuzz/corpus/session fuzz/seeds/session
```

Ввод, который роняет проверку, после исправления ошибки становится затравкой; затравки с
именами `reject-*` должны отвергаться, остальные — приниматься.

Сквозные тесты запускают собранное приложение в настоящем окне как переносную копию в
собственной папке и управляют им сценарием из нажатий клавиш, набранного текста и команд
(возможность `e2e`, `crates/app/src/e2e.rs`); затем тест проверяет отчёты приложения и файлы на
диске и запускает его снова, чтобы увидеть, что сессия вернулась. Во время работы ненадолго
появляются окна; в Linux запускайте их под `xvfb-run`:

```bash
cargo test -p birchpad --features e2e --test e2e
```

Проверки времени — тесты с пометкой `#[ignore = "... run in release"]`: каждая печатает то, что
измерила, и падает, если вышла за свой предел (`birchpad_core::timing::within`). Процесс
Performance выполняет их каждую ночь; чтобы запустить самому:

```bash
cargo test --release -p birchpad-core -p birchpad-io -p birchpad-view -p birchpad-editor -- --ignored --nocapture --test-threads=1
```

Мутационное тестирование проверяет сами тесты: [cargo-mutants](https://mutants.rs) понемногу
меняет код crate'ов без окна (`.cargo/mutants.toml`), и изменение, которого не замечает ни один
тест, — это пробел в тестах. Процесс Mutants выполняет его каждую ночь, по crate'у на задание, и
падает, когда тесты crate'а ловят меньше мутантов, чем его порог в
`.github/mutants-floors.toml`; эти пороги тоже только растут. Выживший мутант получает тест или,
если он не меняет ничего важного, исключение в `.cargo/mutants.toml` с объяснением. Для одного
crate'а:

```bash
cargo mutants --package birchpad-core
```

То, чего не видит ни один автоматический тест (методы ввода, экранные дикторы, дисплеи,
установщики и обновления), проверяется вручную перед каждым выпуском:
[docs/release-checklist.ru.md](docs/release-checklist.ru.md).

### Документация на двух языках

Документы для пользователей и участников написаны на английском и на русском, рядом: README,
CONTRIBUTING, SECURITY, PRIVACY, кодекс поведения, [плагины и скрипты](docs/plugins.ru.md),
[список проверок выпуска](docs/release-checklist.ru.md) и [план развития](docs/ROADMAP.ru.md), у
каждого рядом его `*.ru.md`, со ссылками друг на друга в начале. Изменение одного меняет и
другой в том же коммите. ADR и список изменений — только на английском.

### Версии

Версия рабочей области в `Cargo.toml` — это версия приложения: версия выпуска, задаваемая при
открытии ветки выпуска; её берут `birchpad` и поставляемые с ним инструменты (`birchpad-fuzz`,
`birchpad-release-tool`). У каждого другого crate'а своя версия, и она растёт в выпуске, только
если crate в нём изменился:

- crate, чья папка изменилась с прошлого выпуска (код, тесты, `Cargo.toml` помимо версии),
  получает версию выше прежней — как правило, версию выпуска — один раз, в изменении, которое
  первым трогает его в этом выпуске;
- неизменённый crate сохраняет версию, даже если поднялась версия crate'а, от которого он
  зависит;
- зависимость рабочей области от него (`[workspace.dependencies]`) называет ту же версию.

```bash
cargo run -p birchpad-release-tool -- crate-versions
```

проверяет это относительно тега последнего выпуска (или `--since TAG`); процесс выпуска
выполняет эту проверку перед сборкой.

## Коммиты и pull request'ы

- Используйте [Conventional Commits](https://www.conventionalcommits.org/) (`feat:`, `fix:`,
  `docs:`, `refactor:`, `test:`, `ci:`, `chore:`). Список изменений составляется по ним.
- Держите pull request'ы сосредоточенными: одно логическое изменение на PR.

## Лицензии и сторонний код

Birchpad распространяется по двойной лицензии MIT OR Apache-2.0. Предлагая вклад, вы
соглашаетесь, что он лицензируется так же.

**Не** копируйте код из проектов под GPL (включая Notepad++ и crate'ы редактора Zed) или под MPL
(например, Helix). Совместимость с *форматами файлов* Notepad++ (темы, пользовательские языки,
файлы API) приветствуется.

### Чистая комната

Birchpad заново реализует то, что делает Notepad++, без его кода. Чтобы ничего из него не
просочилось, даже в пересказе:

- **Не читайте исходный код** Notepad++, Scintilla, Lexilla или плагинов Notepad++ (ComparePlus,
  JSON Viewer, XML Tools, Hex Editor, DSpellCheck...), работая над Birchpad, а для данной
  возможности — и других редакторов под GPL или MPL. Тот, кто изучал какую-то часть, оставляет
  её другому.
- **Работайте снаружи:** руководство пользователя (npp-user-manual.org), меню, диалоги и
  поведение программы, какими их видит пользователь, и файлы, которые она читает и пишет.
  Сначала опишите, что строить, своими словами (план развития, ADR), затем пишите код по этому
  описанию.
- **Форматам файлов следовать можно:** имена элементов и атрибутов (`tabColourId`,
  `WidgetStyle`), ключи и значения `session.xml`, `stylers.xml`, `langs.xml`, файлов UDL и API,
  файлов `nativeLang` и параметры командной строки — чтобы Birchpad читал то, что у
  пользователей уже есть.
- **Чужие данные мы не поставляем:** темы, файлы API, коллекция UDL, переводы и списки
  ключевых слов Notepad++ подпадают под его лицензию. Birchpad читает их из файлов самого
  пользователя и поставляет только данные, написанные им самим или под лицензией, совместимой с
  MIT и Apache-2.0 (отмеченной в `deny.toml` или рядом с файлом).
- **Названия пунктов меню и настроек** могут совпадать с названиями Notepad++, чтобы его
  пользователи находили дорогу; более длинные тексты (описания, справка, сообщения) пишутся
  заново. Значки и изображения рисуются для Birchpad или берутся под совместимой лицензией с
  сохранением этой лицензии.
- **Код и данные из других мест** под разрешительной лицензией сохраняют её и уведомление об
  авторских правах, а изменение говорит, откуда они. К коду, написанному с ИИ-помощником,
  применяются те же правила: просите его по описанию, никогда не указывая на исходник под GPL.

Pull request, затрагивающий возможность Notepad++, говорит, по чему она построена
(руководство, поведение, образцы файлов).
